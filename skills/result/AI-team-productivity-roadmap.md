# 全员应用 AI 编码与提效的组织级实战路线图

> 不讲概念，不讲趋势，只讲"每一步怎么做"。

---

## 一、顶层认知 — 为什么"装个 Copilot"不等于落地

### 三个常见误区

| 误区 | 真相 |
|------|------|
| 买了工具 = 提效完成 | 工具只是起点，真正的提效来自流程重构和团队习惯改变 |
| 强制使用 = 能力提升 | 缺乏引导的强制使用只会培养出"接受 AI 一切输出"的坏习惯 |
| AI 替代人 = 裁员 | 在已有项目中，AI 更多是放大人的能力，而非替代 |

### 核心观点

> **AI 提效是系统工程，不是工具安装。**

同时要改三件事：

```
人（技能/心态） ← → 流程（协作方式）
        ↕
   工具（集成/安全/质量）
```

缺少任何一环，落地都会卡在半路。

## 二、成熟度四阶段模型

### Level 1 — 个人尝鲜（1-2 周）

**目标**：每个人建立 AI 辅助编码的习惯。

| 维度 | 实践内容 |
|------|---------|
| **工具** | 选定 AI 编码助手（Cursor / Copilot / Claude Code），统一配置，确保环境一致 |
| **行为** | 每人每天至少 5 次 AI 交互，刻意练习写 Prompt 而非直接编码 |
| **度量** | 统计"AI 辅助代码行数占比"，目标 > 20%（团队内部匿名看板） |

**三个"零门槛" Prompt 模板（全员必学）：**

```
模板一 — 注释生成函数：
"根据以下注释生成 [语言] 函数：[注释内容]"

模板二 — 解释陌生代码：
"逐行解释 [文件:行号] 的功能，用最简单的话说"

模板三 — 生成单元测试：
"为以下函数生成完整的单元测试，覆盖正常、边界和异常情况"
```

---

### Level 2 — 小组试点（2-4 周）

**目标**：选定一个模块跑通"AI 优先开发"完整流程，沉淀 SOP。

| 维度 | 实践内容 |
|------|---------|
| **流程** | 选定 1-2 个低风险模块做"AI 优先开发"试点。建立 AI 代码 Review 标准（什么必须人审、什么可信任 AI） |
| **知识** | 建立团队 Prompt 模板库，按场景分类（CRUD / 重构 / 测试 / 文档 / Bug 修复），每周新增 |
| **工具链** | 接入 AI Code Review 工具、AI 辅助 PR 描述和变更日志生成 |

**试点阶段的核心规则：**

```
AI 优先开发流程：
1. 需求 → 开发者写技术方案（AI 协助）
2. 开发者写 Prompt → AI 生成初版代码
3. 开发者 Review 逻辑 + AI Review 风格/规范
4. 合并前：AI 生成变更摘要
5. 合并后：AI 辅助分析测试失败原因
```

---

### Level 3 — 全组推广（2-4 周）

**目标**：将 AI 辅助写入团队日常开发规范，覆盖全部项目。

| 维度 | 实践内容 |
|------|---------|
| **流程** | 将 AI 输出质量纳入 Code Review 标准。建立"谁生成的 Prompt 谁对代码负责"机制 |
| **知识** | 定期 Prompt Workshop，互相 review prompt 质量。沉淀反模式案例（哪些 Prompt 产出过坏代码） |
| **工具链** | 接入 AI 知识库工具（项目级上下文理解），自定义 AI 规则（编码规范、命名规范、安全规则） |

**Prompt 模板库管理方法：**

```
/team-prompts/
├── bug-fix/          # Bug 修复场景模板
├── new-feature/      # 新功能增量开发
├── refactoring/      # 重构（不改行为）
├── new-module/       # 新模块设计
├── testing/          # 测试生成
├── code-review/      # Review 辅助
└── documentation/    # 文档/方案生成
```

每个模板包含：
- 适用的前置条件
- 完整的 Prompt 文本（可直接复制使用）
- 预期输出格式
- 使用后的注意事项

---

### Level 4 — 流程重构（持续）

**目标**：重新定义开发工作流，人和 AI 各自做最擅长的事。

| 维度 | 实践内容 |
|------|---------|
| **流程** | AI 写初稿 → 人做架构决策和终审。PM 用 AI 写技术方案初稿，开发者 Review 和修正 |
| **组织** | 设立"AI 提效工程师"角色（非专职，轮值），负责 Prompt 库维护、新工具评估、效果数据统计 |
| **度量** | 持续跟踪：交付周期缩短率、Bug 率变化、开发者满意度 |

**"AI-first"技术方案模板：**

```
## 技术方案标题

### 背景与目标
[用 AI 生成初稿，人补充上下文]

### 方案对比
方案 A（推荐）：AI 生成优缺点分析
方案 B：AI 生成优缺点分析

### 影响范围
AI 标注所有需要修改的模块和文件

### 实施步骤
AI 生成步骤，人确认顺序和依赖

### 风险和回退方案
AI 列出风险，人补充经验判断
```

## 三、最容易踩的 5 个坑（附解法）

### 坑 1：Prompt 质量参差不齐

**现象**：同一件事，有人 3 分钟搞定，有人折腾半小时。

**解法**：
- 建 Prompt 模板库，从"每个人自己写"变成"先用模板，再个性化调整"
- 模板纳入 Code Review：PR 里的 AI 生成代码必须注明使用的 Prompt
- 每月一次 Prompt 品鉴会：投票选出"本月最佳 Prompt"和"本月回炉 Prompt"

### 坑 2：AI 代码质量无人兜底

**现象**：AI 生成的代码跑过了测试但隐藏了逻辑漏洞，上线后出问题。

**解法**：
- **硬规则**：AI 代码必须经过人 Review 才能合并，不允许直接合并 AI 分支
- Review 时要求开发者回答："你为什么接受 AI 这个实现方案？有没有更好的方案？"
- 对 AI 生成代码单独标记，追踪 Bug 率

### 坑 3：上下文割裂

**现象**：AI 每次只看到单个文件，生成代码风格与项目不一致，或忽略了已有的设计约束。

**解法**：
- 从"单文件 Prompt"进化到"将项目上下文通过 `AI_CONTEXT.md` 投递给 AI"
- 增量开发场景下，至少提供：项目架构摘要 + 要改的 2-3 个文件
- 参考下一章的**上下文管理策略**

### 坑 4：躺平依赖 AI，不思考

**现象**：开发者变成"AI 生成器的操作员"，不再理解自己合入的代码。

**解法**：
- Review 时要求开发者解释为什么接受 AI 的方案（"这个方案和你的思路有什么不同？"）
- 关键模块（支付、权限、数据处理）禁止纯 AI 生成，必须有人手工实现核心逻辑
- 定期做"无 AI 日"：每周半天关掉所有 AI 工具，手写代码

### 坑 5：提效数据不可见

**现象**：大家感觉"好像快了一点"，但没有数据支撑，管理层看不到 ROI。

**解法**：
- 建简单看板，3 个核心指标：
  - PR 提交到合并的周期时间
  - 单元测试覆盖率变化
  - 开发者每周"纯编码时间"占比
- 每个月出一次 AI 提效数据报告，用数字说话

## 四、重点场景：已有项目的增量迭代开发

> 大部分团队面对的不是新项目，而是几十万行代码的老项目。AI 在增量场景下最大的挑战不是"写不出代码"，而是"看不懂上下文"。

### 4.1 增量开发的 AI 工作流（三步法）

```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   第一步         │    │   第二步         │    │   第三步         │
│   理解上下文      │ →  │   生成变更        │ →  │   验证集成        │
│   投入 70% 时间  │    │   投入 20% 时间   │    │   投入 10% 时间   │
└─────────────────┘    └─────────────────┘    └─────────────────┘

  让 AI 先"读"再"写"    基于理解产出方案       生成变更前后对比
  先总结当前逻辑         附带影响范围说明       标注手工测试点
```

### 4.2 四类增量场景及 Prompt 模板

#### 场景 A：给已有函数加新功能

```
请修改 [文件A] 的 [函数X]，增加 [功能Y]。

要求：
1. 先列出该函数当前的所有输入、输出和副作用
2. 用注释标注哪些行保持不变，只输出需要修改的部分
3. 说明此次修改会影响哪些调用方
4. 生成代码的风格必须与文件现有风格一致
   （特别注意：命名方式、错误处理模式、日志格式）
```

#### 场景 B：修复遗留 Bug

```
[文件路径] 的第 [行号] 出现 [Bug 现象]。

请按以下顺序分析：
1. 追踪该变量的完整数据流（从哪里来，经过哪些变换）
2. 列出可能出错的 3 个原因，按概率排序
3. 对每个原因给出修复方案和影响范围
4. 推荐最优方案并解释理由

在确认方案前，不要生成修复代码。
```

#### 场景 C：重构旧代码（不改行为）

```
对 [文件/模块] 进行重构，约束条件如下：

1. 不得修改任何外部接口签名（函数名、参数、返回值类型）
2. 不得修改业务逻辑
3. 重构范围限定在 [函数A] 内部
4. 如果涉及提取新函数，新函数必须是 private/internal
5. 重构完成后输出变更前后 diff 对比
6. 最后输出自动化测试建议，验证行为未改变
```

#### 场景 D：在老项目上新增一个模块

```
我需要在 [项目名] 中新增 [模块名] 功能。

第一步 — 分析：
请分析项目中已有的类似模块 [参照模块路径]：
1. 它的目录结构、命名规范、分层方式
2. 它的错误处理模式、日志方式、配置加载方式
3. 它的测试风格和组织方式

第二步 — 设计：
按完全相同的风格，设计新模块的结构。
在确认设计方案后再逐步生成代码。
```

### 4.3 上下文管理核心技巧

增量开发中，限制 AI 最大的因素不是模型能力，是**上下文窗口的利用效率**。

#### 策略一：金字塔式上下文投递

```
不这样做：
  把整个项目扔给 AI → "帮我改一下订单模块"

而是这样做：
  第一层：项目架构概述（200 字，写进每个 prompt 开头）
  第二层：要修改的模块说明（数据结构 + 核心流程）
  第三层：具体要改的 2-3 个文件的完整代码
```

#### 策略二：建立 `AI_CONTEXT.md`

在项目根目录维护一份上下文文件，每次请 AI 改代码前先投递它。约 1K tokens，回报极高。

```
# AI Context — [项目名]

## 技术栈
- 语言 / 框架 / 版本
- 构建工具和测试框架

## 架构风格
- 分层方式（DDD / MVC / Clean Architecture）
- 依赖注入方式
- 数据库访问层模式（ORM / Raw SQL / Repository）

## 编码规范
- 命名约定（驼峰/下划线、缩写规则）
- 错误处理模式（返回值 / 异常 / Result 类型）
- 日志规范（日志级别、格式、关键字段）

## 关键模块地图
- src/modules/* 的职责边界
- 核心数据流图（文字版）
- 配置文件和环境变量说明

## 常见模式（供 AI 生成时参考）
- 如何新增一个 API 端点（步骤 + 需要改哪些文件）
- 如何新增一个数据库迁移（步骤 + 命名规范）
- 如何新增一个定时任务（步骤 + 注册方式）
```

#### 策略三：按变更类型控制上下文量

| 变更类型 | 需要读取的文件 | 上下文量级 |
|---------|--------------|-----------|
| 修 Bug | 1-2 个相关文件 | 2-5K tokens |
| 加小功能 | 相关函数 + 调用方 | 5-10K tokens |
| 加新模块 | 架构摘要 + 参考模块 | 10-20K tokens |
| 大规模重构 | 架构摘要 + 核心文件 | 20-50K tokens |

### 4.4 增量变更的 Review Checklist

| 检查项 | 负责方 | AI 协助方式 |
|--------|--------|------------|
| 是否修改了不该改的行 | 人 | AI 生成"变更摘要"标出所有修改点 |
| 变更是否覆盖所有调用方 | AI + 人 | AI 搜索引用并列出所有受影响位置 |
| 新代码风格是否与旧代码一致 | AI | AI 对比风格差异，标出不一致处 |
| 是否引入了新的外部依赖 | AI | AI 检查 import 变更和 package.json 变化 |
| 边界条件是否处理 | AI + 人 | AI 列出边界条件，人确认 |
| 测试是否覆盖新路径 | AI | AI 建议测试用例 |

#### 实操流程

```
[Prompt]  →  AI 生成代码 + 影响范围说明
                         ↓
              开发者做"语义 Review"
        （重点看逻辑正确性，不看格式/命名）
                         ↓
              AI 根据 Review 意见修改
                         ↓
              运行全部测试 + AI 分析失败
                         ↓
              合并前 AI 生成最终变更摘要
```

## 五、可立即落地的 3 个行动

### 本周

- [ ] 全员完成 1 次 AI 编码工具配置
- [ ] 全员掌握 3 个基础 Prompt 模板（注释→函数、解释代码、生成测试）
- [ ] 选定 1 个低风险模块作为 AI 优先开发试点

### 本月

- [ ] 建立团队 Prompt 模板库（超过 5 条按场景分类的模板）
- [ ] 在试点项目中建立 `AI_CONTEXT.md` 并试用
- [ ] 输出第一份 AI 提效数据（PR 周期、AI 辅助率）

### 本季度

- [ ] 完成第一次 AI 提效复盘，调整流程和工具链
- [ ] Prompt 模板库沉淀到 20 条以上，覆盖所有常见开发场景
- [ ] 建立增量开发的 Review Checklist
- [ ] 沉淀至少 5 个 AI 辅助开发的"翻车案例"和"高光案例"

---

> **核心思想**：AI 编码提效不是一场工具升级，而是一次开发方式的重构。从个人习惯到团队流程，从顶层设计到每行代码，脚踏实地，分阶段推进。
